## Objective

Rework the `PDF Generator` page section (`ExportPdf.jsx`) so an author can export a plan from the site
they are on, and the export prints the pages they picked. Owner asks (2026-10-30):

1. **The plan picker is subdomain-scoped.** Only patterns mounted on the current host are offered.
   A plan that lives on another subdomain is never listed.
2. **Find and fix the component's other problems** (audit below).
3. **Keep the zip download.** Merged plans can be large, so the server keeps returning the PDF inside
   a zip.

The route itself (dms-server has no `downloadpdf`) is tracked separately in
`pdf-export-route-missing-on-dms-server.md`, which so far exists only on the `permissions_move` branch
(not yet merged to master). The owner wants it fixed in this sweep, so it is phase 4 here and that task
closes with this one once both are on master.

## Proposed changes

### Phase 1: plan scoping and correct URLs (fixes 1-3). DONE 2026-10-30

- Move the mount logic out of the router into a shared util so the router and the section use one
  definition: `packages/dms/src/utils/patternMounts.js` exporting
  - `getPatternMounts(pattern)` (moved from `render/spa/utils/index.js`, unchanged), and
  - `mountsForSubdomain(pattern, subdomain)`, which is the filter at `render/spa/utils/index.js` ~448-453,
    `ROOT_SUBDOMAIN_ALIASES` included, returning the matching mounts with `navPrefix`.
  - `render/spa/utils/index.js` imports both. Routing behaviour is byte-for-byte unchanged.
  - It lives in `utils/` because patterns don't import from `render/` or from each other.
- The router already has the normalized `SUBDOMAIN`. Pass it down with the page config as
  `subdomain` and expose it on `CMSContext` (`patterns/page/siteConfig.jsx`), next to `sitePatterns`.
- `ExportPdf.jsx`: options = page-pattern rows with at least one mount for the current subdomain. Keep
  each option's resolved mount (`base_url`, `navPrefix`). Default = the current pattern.
  When only one plan matches, show its name as plain text instead of a picker (mockup).
- Build the tree with the shared `dataItemsNav(pages, baseUrl)` from `utils/nav.js` (fixes 13), passing
  `navPrefix + base_url` of the matched mount, so page paths come out the way the site nav builds them.
  Page URL = `origin + path`; the cover goes through the same builder.

### Phase 2: request and selection correctness (fixes 6-9, 12-16). DONE 2026-10-30

- Drop the per-page `apiLoad` loop. The list call already returns what the request needs.
- Send the pages as an ordered array `[{ url, title, depth }]`; the contents page is built from it on the
  server (no title-keyed object). Only the new route reads this shape; the old avail-falcor route is not used.
- Cover and contents are independent. Cover single-select gets a "None" option. Nothing is auto-picked.
- Abort or ignore stale `fetchPages` responses (an `ignore` flag in the effect cleanup). Clear the selection when the list
  for a new plan arrives.
- `selectablePDF.js` is deleted. `patterns/page/components/saveAsPDF/pdfExport.js` holds the tree helpers
  (`buildPageTree`, `printableIds`, `selectedInOrder`, `filterTree`, `fileNameFor`) and the job calls
  (`startPdfExport`, `pdfExportStatus`, `cancelPdfExport`, `downloadPdfExport`), which throw `{ message, status }`
  instead of logging. The zip download is kept, named `<file_name>.zip`.
- Deviation: the tree uses the shared `navPath` (now exported from `utils/nav.js`), not `dataItemsNav`, because
  the nav builder drops `hide_in_nav` children and drafts; the export lists both (drafts greyed).
- Order selected pages by tree walk (the order they print in), no `index` sort.

### Phase 3: the UX from the mockup (fixes 5, 10, 11). DONE 2026-10-30

- Tree with checkboxes and a part-ticked state (the `UI` checkbox primitive; add a named style if it lacks
  an indeterminate look), its own expand chevron, expand all, page filter, and a selected count.
- Drafts listed greyed with a "draft · not exported" mark; "hidden in nav" marked.
- Document card: cover (with None), contents switch, file name, the "In this PDF" outline in print
  order, and the export button with page count.
- States: exporting (elapsed time, indeterminate bar, button locked), done (Download again), failed
  (server message, Try again), service missing (404), signed out (Sign in), nothing selected, no
  cover pages, plan with no published pages.
- All classes under a `pdfExport` key in `patterns/page/defaultTheme.js` (`ExportPdf.theme.js` sibling).
  Legacy themes get their pre-port values via `_legacy/pages.js`, as in the v6 port.

### Phase 4: the server route (fix 4, 17, and the route task). DONE 2026-10-30 (not deployed)

Owner decisions 2026-10-30; everything below follows from them:
- Port puppeteer into dms-server. The image had no Chromium (`Dockerfile` installs only GDAL, build tools and
  `zip`; the deploy's Chromium is Playwright on the host for smoke tests), so the image gains Debian's
  `chromium` and the server uses `puppeteer-core` (no bundled browser download).
- **Export needs no permission.** The most anyone gets from the route is pages they could open anyway.
- **Two modes, default `public`.** `public`: no token is sent, so headless Chrome sees what an anonymous
  visitor sees (also what a signed-in author gets when they pick public). `self`: the client sends its token
  and the headless page runs with it in `localStorage.userToken`, so the PDF shows what that person sees.
  A page the viewer can't open is **left out** and listed in the job's `skipped` (a redirect away from the
  URL, or the page's no-access marker).
- Pages load data dynamically and some take a while, so readiness is waited for, not guessed (below).
- The PDF must look like the site: same layout width, fonts, colors and print CSS, with the nav chrome hidden.

**Jobs, not one long request.** mercury's nginx proxies with `proxy_read_timeout 120s`
(`deploy/sites_https.mjs`), and a 200-page plan takes minutes. So:
- `POST /pdf/export` `{ pages: [{url, title, depth}], cover_url, toc, file_name, mode }` (+ `Authorization`
  only in self mode) → `{ id }`. The id is a random UUID, and it is the only key to a self-mode PDF.
- `GET /pdf/export/:id` → `{ state: queued|running|done|failed, done, total, current, skipped, error }`.
- `GET /pdf/export/:id/file` → `<file_name>.zip` holding `<file_name>.pdf` (the zip stays because files can be large).
- `DELETE /pdf/export/:id` cancels. Jobs and their files are dropped an hour after they finish.
- One export runs at a time (`DMS_PDF_CONCURRENCY`, default 1), one browser per job, and an incognito context
  per job (no localStorage carried between jobs). Validation: 1–1000 http(s) pages, all on one origin,
  which must equal the request's `Origin` when the browser sends one.

**Readiness per page** (`waitForReady`): navigate (`domcontentloaded`), then poll every 250 ms until, for
1 s straight, (a) no HTTP request is in flight (websockets and event streams are ignored; a request open more
than 30 s is treated as a stream), and (b) nothing in the DOM carries `data-dms-loading`. Then scroll the
page through to trigger lazy sections, and wait again. The budget per page is `DMS_PDF_PAGE_TIMEOUT_MS`
(default 120 s). Past the budget the page prints as it is, and the job reports it.
- New generic client contract: **a section sets `data-dms-loading` while it fetches.** dataWrapper does it
  from `useDataLoader`'s `loading`. Any other component that loads data can opt in the same way.
- New no-access marker: `data-dms-no-access` on the page pattern's no-permission screen.

**Looking like the site.** The layout width is 1200 CSS px, printed at scale `printable width / 1200`, so the
PDF gets the desktop layout, not the 816 px tablet one. Print media is on (so the site's `print:` rules apply),
with the light color scheme and backgrounds. Site nav is hidden: `Layout.jsx` wraps TopNav and SideNav in a
`display: contents` element carrying `data-dms-chrome`, and the exporter hides `[data-dms-chrome]`.
There is no DOM or style change on the live site. `canvas` elements (maps, WebGL) are swapped for a screenshot
of themselves before printing, since headless print renders WebGL blank. Page margins are painted with the
page's own background color, and page numbers go in the bottom margin in the page's text color.
Contents page: rendered inside the first exported page (so the site's fonts and CSS are loaded), with the
body replaced by the list and styled from that page's computed `h1` and body styles. No MNY-specific
fonts or images (the old route hard-coded Oswald and `topolines.png`).

## Owner test round 2026-10-31 (mitigateny_2025: Home + Know the Environment, prod data, read-only)

Reported: count reads "1 of 0" while pages load; sometimes "This plan has no published pages" until the
plan is switched away and back; the building hint is too long; the PDF overlaps content and has the wrong
background (`~/Downloads/test (1)/test.pdf`).

- **Overlap: cause.** Chrome's own pagination re-flows the page grid at each sheet break. An item pushed
  to the next sheet (images had `break-inside: avoid`) doesn't push its grid siblings, so they overlap.
  **Fix:** `render.js` prints each page as ONE sheet as tall as the page (`printTall`) and `appendPdf`
  slices it onto Letter sheets with pdf-lib (each page embedded once as a form XObject, clipped per sheet).
  `sheetCuts` picks the lowest cut in each sheet's lower half that crosses no span (`measure`: every text
  line, img / svg / canvas / tr / control, every painted box under half a sheet). A `.print-page-break`
  (MNY's header emits one) still ends a sheet, moved down to the first clear spot when it sits inside
  something (Home's marker is mid hero photo).
- **Tall print side effect:** `vh` in print is a share of the sheet, so `min-h-screen` grew to the whole
  page and pushed the rest off. `freezeViewportHeights` pins every vh / vmin / vmax declaration (stylesheet
  rules incl. `@layer` / `@media`, and inline styles) to its on-screen px before printing.
- **Second overlap: grid rows in paged layout.** Even on one tall sheet Chrome lays grids out in paged
  mode and sized MNY's hazard-card rows differently (cards grew ~136 px into the pagination below). Ruled
  out by test: vh, the window size, html/body % heights, the image's `margin-top: -150px`, `flex-col-reverse`,
  and making the root monolithic (`overflow` / `contain`: Chrome then paints only ~1000 px). **Fix:**
  `freezeGrids` pins every grid's `grid-template-rows` / `-columns` to the px they resolve to on screen;
  that print matches the screen.
- Contents heading uses the page's h1 font but the body text colour (Home's first h1 is white on the hero).
- **Background: cause.** The margin colour was sampled at the page's top centre, which on Know the
  Environment is the navy hero, so every margin went navy. MNY's real surface is a 96% grey gradient over
  `topolines.png` with no background-color, which the old code couldn't read. **Fix:** a second print of
  the same page with everything hidden except the layout surface (the ancestors of `data-dms-chrome`, or
  body) is drawn under each sheet, over a fill of the surface colour (its background-color, or its
  gradient's first colour). The contents page copies the surface's background onto its body.
- Cover: `appendPdf(..., { fit: true })`, the whole page scaled onto one sheet (it printed 2 before).
- Client: count hidden while loading and the selection cleared when a load starts; an empty list is
  asked for twice more (0.5 s, 1.5 s) before the plan is called empty, since `dmsDataLoader` swallows
  request errors and returns `[]`; the empty state has "Check again". Root cause of the empty first load
  not confirmed (no browser access to the owner's session); a swallowed Falcor error is the likely path.
  `buildPageTree` compares ids as strings (sync mirror ids are strings, `parent` may be a number).
- Building hint is now "Don't close this tab while the PDF is building."
- Verified locally against :5173 (anonymous GETs only, no writes) with a driver in the session scratchpad.

## Owner test round 2026-11-02 (`~/Downloads/mitigateny_2025.pdf`)

Reported: export still slow; the draft / hidden-in-nav marks look like buttons; content still breaks at
odd places, the header alone on a sheet "just for some white space"; should pages carry page-break elements?

- **Slow: cause.** mitigateny's site has sync on (`VITE_DMS_SYNC=1`), so every export tab downloaded the
  whole pattern (`/sync/bootstrap`, ~30 s, open the whole time) and the readiness wait waited for it.
  Timed locally: ~33 s of a page's ~36 s was that wait, the print itself under 2 s. **Fix:** `openTab`
  wraps `fetch` so `/sync/*` is refused in export tabs; the client falls back to the API (its offline
  path). Same measurements and print size after. Per page now ~8-20 s locally, the spread being the
  site's own data queries.
- **Also faster:** a job prints `DMS_PDF_TABS` (default 3) pages at once in tabs of its browser; the cover
  renders and the contents page's tab loads (`openStyleTab`) alongside them. Two pages + cover + contents:
  18-40 s locally (was ~2.5 min). Parallel tabs gained less than expected here (the local API is the
  bottleneck): 32-34 s vs 37-38 s for the two pages.
- **Header alone on a sheet: cause.** MNY's header (`mnyHeaderDataDriven.jsx`, theme and library copies)
  emitted a `.print-page-break` after itself. Removed; the cut now goes where the content allows.
- **Authored breaks:** the rich-text editor already has a Page Break block (`/page break`,
  `figure[type=page-break]`); the renderer now ends a sheet there and hides the bar. `.print-page-break`
  still works.
- **Cut choice** (`sheetCuts`): a heading and the first line after it are one span (no orphan headings);
  among clear spots in the sheet's lower half it takes the lowest that crosses the fewest big painted boxes
  (`measure` → `boxes`), so a table or card moves whole when it can; the next sheet starts at the next
